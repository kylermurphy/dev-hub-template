# Decisions

Why dev-hub's workflow is the way it is. One dated line per decision, newest first, with the
PR that made it. **Read this before changing a rule**; when you change one, edit `CLAUDE.md`
first, then its summaries, and add a line here.

Repo-specific decisions don't go here; they go in that repo master's `## Learnings` as
`Decision:` lines.

**Rules for this table**
- **Where** is the PR that made the decision, as a link: `[#N](https://github.com/<owner>/dev-hub/pull/N)`.
  Never write "this PR": open the PR first, then fill in its number in a follow-up commit.
  `template v0.1.0` marks decisions inherited from the dev-hub template; add your own rows
  above them.
- **Superseded decisions stay.** Add the new decision as a new row above, and end the old
  row's Decision with "*(superseded: see <date> row)*". Don't rewrite history.

| 2026-09-29 | Multi-month research projects live in `projects/`: one file per project (descriptive file name, short uppercase `id` in a one-line-per-field metadata block), built from `projects/TEMPLATE.md` with fixed sections (Summary, Background, Science goals, one `### O<n>` subheading and work-package table per objective, Plans, Next actions, References, Decisions, Research log). `projects/INDEX.md` is the portfolio. Commands `new-project`, `plan-project` (which waits for the owner's go) and `review-projects` (flags active projects idle for 30 days). Edits go straight to `main`; work packages link to board IDs one way only; `check-board` validates the structure; project files stay private to your hub. | A strategic layer above the boards, in Markdown, that agents can plan from. A fixed structure with stable IDs makes "plan WP1.2" unambiguous. Deliverables and deadlines are left for later so it stays light. | template v0.2.0 |
| 2026-09-29 | `plan-task` always plans, discusses and **waits for the owner's explicit go**. Answers to its questions, earlier discussion or "plan and do" aren't a go. New `run-task <ID>` is the path that doesn't wait: Claude writes and saves its own plan (S/M tasks with a clear definition of done; not L, not needs-a-decision, not features) and goes to a draft PR. Every plan names who does each step (main model or a subagent). One "When to stop and ask" list (unclear definition of done, an unsettled design choice, anything irreversible or outside the branch, work bigger than the row, repeated failures) governs `run-task`, `multi-task`, `pickup-task` and overnight runs: ask in chat if the owner is present, else `Blocked`. | `plan-task` runs went from plan to commits without the discussion step: step 2 said "discuss" but never "wait". A separate command makes not waiting an explicit choice, and concrete stop rules replace "ambiguous or irreversible". | template v0.2.0 |
| 2026-09-29 | Larger work in one repo is a **feature** on `FEATURE_BOARD.md`: IDs `<PREFIX>F<letter>` with subtasks `<feature ID><n>`, one long-lived branch `feature/<ID>-<slug>` and one draft PR. Subtasks are committed straight onto the branch (ID-prefixed commits, the default branch merged in first) with no PR, log or `TASK_LOG.md` row of their own. A subtask is `Done` once its commits are on the branch and checks pass; the feature only via `mark-done`. New command `new-feature`; the lifecycle commands take feature and subtask IDs. | Some work (L tasks, a new module) shouldn't reach `main` piecemeal. GitHub Projects and feature flags were considered: the first leaves Markdown, the second is awkward for research code. | template v0.2.0 |

| 2026-09-29 | On `TASK_BOARD.md` each Status is written icon + word (`⏩ Todo` · `🟠 WIP` · `‼️ Blocked` · `🛑 Usage-stopped` · `🟢 Done`), with the exact strings defined once in `CLAUDE.md`; `TASK_LOG.md` and logs keep the word alone.
